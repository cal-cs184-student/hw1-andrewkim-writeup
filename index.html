Task 1: Drawing Single-Color Triangles

Rasterization is the process of taking some 3D geometric object that we want to sample and converting it to the 2D screen we want to display it on. We are essentially “flattening” the object, and we can do so by breaking it down into many triangles to display.

In order to rasterize a single triangle, I modified rasterize_triangle() to iterate through each pixel on the screen and determine whether or not its center (x-coordinate + 0.5, y-coordinate + 0.5) lies inside the triangle. This is done through a binary process: if it does, we fill in that pixel, and if it doesn’t, we don’t, constructing the triangle pixel by pixel. To do this, we use the help of what is called the Point-in-Triangle Test. In this test, each edge of the triangle defines what are called half-planes where the triangle itself is the intersection of three half-planes. For each edge, we determine which side a pixel lies using a mathematical formula that returns a positive number if the pixel is “inside” the edge, a negative number if the pixel is “outside” the edge, and 0 if it lies on the edge. In my implementation, a pixel that lies on an edge is considered inside the triangle, though an improved one would include the OpenGL/Direct 3D Edge Rules to tie-break edges shared by two triangles. If all three edges collectively return a number >= 0 or <= 0 (depending on the winding order of the vertices), then that pixel is inside the triangle.

To make the process more efficient, my algorithm only checks each sample within the bounding box of the triangle, which is the smallest rectangle that can be drawn around the triangle while ensuring the entire triangle is inside it. To find the bounding box, I pulled the minimum and maximum x and y values out of the three vertices given to define the corners of the box. Then, I created a nested loop to iterate through its rows and columns, determining each pixel’s location relative to the triangle and filling them in appropriately. This process uses a helper function isInsideTriangle() that implements the binary process and the Point-in-Triangle Test described above. Since my algorithm checks each sample within the bounding box once, it can therefore be no worse than any algorithm that checks each sample within the bounding box of a given triangle.

I ran into some problems where my images weren’t rendering and I was left with either the outlines of some objects or a completely blank screen, so I knew there was a problem with filling in the pixels. To debug, I began with a smaller problem and worked towards the more complicated one as we learned in lecture. Task 2: Antialiasing by Supersampling

Aliasing is a visual defect that occurs when diagonal or curved lines appear jagged and staircase-like because of the pixel grid of the display. Anti-aliasing techniques are those used to help alleviate this effect. In this task, I implemented supersampling, which is an anti-aliasing technique that renders an image at a much higher resolution before downsampling it to the display.

To begin the supersampling process, I began by modifying both set_sample_rate() and set_framebuffer_target() in order to expand our sample buffer based on sample_rate for each pixel that gets added. Our sample buffer can be thought of as a high resolution grid that is implemented as a 1-dimensional, dynamically resizable Color array and is where we will temporarily store the colors of each subpixel which will be useful later on. Its expansion could be done when the user either resizes the window or changes the sample rate.

Next, I modified rasterize_triangle() from task 1 to iterate through each subpixel within a given pixel. Using various details about the whole pixel, I found the coordinates of the centers of each subpixel to pass into our isInsideTriangle() helper function. I either set that subpixel’s location in sample_buffer to color or did nothing depending on whether it isInsideTriangle(), where its location in sample_buffer is calculated using the pixel’s original index, the screen width, and sample_rate. This process fills up sample_buffer with each subpixel’s color.

Finally, I modified resolve_to_framebuffer() to complete the supersampling process. I iterate through each pixel’s subpixel group in sample_buffer, adding up the red, green, and blue components of their colors. They are then each divided by sample_rate to get the final shades of red, green, and blue to determine the final blended color for the entire pixel. This final color is then assigned in the pixel’s location in rgb_framebuffer_target, a 1D array that represents the final image displayed on our screen.

Collectively, the supersampling process is very useful because by assigning pixel colors to the average color of their subpixels, we smoothen out the transitions in pixel color in jagged edges by blending them together. To antialias our triangles using supersampling, we rendered the image at a higher resolution and stored it in sample_buffer before transferring it to our frame buffer with the appropriate shades of color for each pixel.

Displayed above are results of sampling an image using different sampling rates. Zooming in on the right vertex of the red triangle, we can see the difference supersampling makes. Sampling just once per pixel gives us jagged edges as well as inconsistent colorings where pixels are separated from each other. However, supersampling at 4 and 16 subpixels/pixel gives us very well blended corners where these inconsistent colorings are reduced since the transitions use different shades of red across more pixels.

On a final note, in addition to the modifications to the rasterization pipeline explained above, I also modified fill_pixel() to account for rendering issues regarding points and lines after the supersampling modifications, since points and lines aren’t anti-aliased. To do this, I filled each subpixel within a given pixel all to be the same color the pixel should be.

Task 4: Barycentric Coordinates

Barycentric coordinates are a coordinate system used to smoothly interpolate attributes on the surface of an object, such as a triangle. One common example is interpolating the colors of the three vertices of a triangle to create a blended result. Given a point P within a triangle, we can determine its color based on these coordinates that show the influence each vertex has on it defined by the scalars, or “weights”, (alpha, beta, gamma). The more a point moves towards a vertex, the higher that corresponding weight becomes and vice versa. Another way to look at these coordinates is the distance traveled to a point from the opposite edge. All weights add up to 1 where each weight must be non-negative for the point to lie within the triangle (including on edges).

We can think of each vertex as having a “gravitational pull” on a point. For example, in the image below we have four points located inside the triangle with alpha corresponding to red, beta corresponding to green, and gamma corresponding to blue:

The point on the red vertex is completely red since it lies directly on the vertex, so its barycentric coordinates are (1.0, 0.0, 0.0).

For the point that lies halfway along the red-green edge, its weights are equally split between red and green (and none for blue), so we get a blended red-green color where its barycentric coordinates are (0.5, 0.5, 0.0).

For the point directly in the center of the triangle, all three vertices are equally influencing its color, so its barycentric coordinates are (0.333, 0.333, 0.333).

For the point shifted towards the blue vertex, its color is predominantly blue with very little red and green influence, though they are still present, so we get a blended red-green-blue color that is more blue defined by the barycentric coordinates (0.10, 0.20, 0.70).

Task 5: "Pixel sampling" for texture mapping

Texture mapping is the process of “wrapping” a 3D object with some 2D texture. We can think of it like “shrink wrapping” a 2D plane onto some object or gift wrapping a box to give it certain colors, textures, geometry, etc. without needing to form each individual detail on the object itself.

In the context of texture mapping, pixel sampling is the process we use to map each location on our object to a location on the texture. Our location on the texture image is represented as a percentage of the image size, (u,v), where we look up the location on the texture, grab the color there, and fill the pixel on the screen with that color. We do this for the entire object to “wrap” it in our desired texture in order to recreate the original image as best as possible.

To implement pixel sampling and use it to perform texture mapping, I began by modifying rasterize_textured_triangle() using logic from previous tasks to find the bounding box of the triangle, iterate through each subpixel in it, and check to see if they are inside the triangle. If a subpixel is inside, I calculated its barycentric coordinates using the formulas seen in class (and used in task 4) and used them to determine the interpolated texture coordinates for the subpixel. Finally, I found the texture color based on whether the sampling method was nearest neighbor or bilinear interpolation by calling either sample_nearest() or sample_bilinear(), with mipmap level 0 for this task, ending the function by writing the appropriate color to our sample_buffer.

These sampling methods are two common methods used to determine what color a pixel should be when our texel coordinates, the location on the 2D texture, do not lie perfectly on any individual pixel. To determine what texel to return, they use different approaches. Nearest neighbor sampling simply grabs whichever texel is closest to the coordinate by rounding to the nearest whole texel and returning it. Bilinear pixel sampling, on the other hand, takes each of the four surrounding texels and blends them together, returning a more smooth result.

To implement sample_nearest(), I converted the normalized UV coordinates to texel coordinates by scaling them by the texture’s width and height, rounded to the nearest integer, and returned the closest texel. For sample_bilinear(), I converted the percentages to the pixel address, found the four nearest pixels as well as their colors, calculated the horizontal and vertical interpolation offsets, and used them all to interpolate the four colors to return the final blended result.

Nearest at 1 sample/pixel: Very blocky with rough transitions in color for Italy, especially darker areas. The longitude line also has very clear differences in its shades of white.

Bilinear at 16 samples/pixel: Best looking result. The transitions from darker to brighter areas of Italy are very smooth and the longitude line is a very consistent shade of white.

There would be a large difference between these two methods during magnification (as seen in this example). When magnified, nearest creates sharp, block-like results since it just grabs the nearest texel color and has to stretch it across multiple pixels, creating high-frequency discontinuities. Bilinear on the other hand, blends the surrounding texel colors together by acting as a low-pass filter, creating a much smoother result.

Task 6: "Level Sampling" with mipmaps for texture mapping

When an object on our screen moves further away from us, a single pixel will end up covering more area of the texture as that object gets smaller (minification). As a result, visual artifacts will appear because we are trying to “squeeze” the full resolution of our texture in a small pixel space. To account for this, we use a series of pre-calculated versions of our texture called mipmaps that decrease in size and by half the resolution at each level. Level sampling is the process of determining which of these layers to use when rendering pixels on the screen. It is a form of pre-filtering anti-aliasing that is intended to prevent these artifacts from forming when textures are viewed from a distance or at angles.

To implement level sampling for texture mapping, I began by modifying rasterize_textured_triangle() by creating and calling a helper function, calculateBarycentric(), to not repeat my logic used elsewhere. This helper function was also integrated into task 4. As we iterate through every pixel and subpixel, if the current subpixel is inside the triangle, calculateBarycentric() is used to calculate the barycentric coordinates for the current subpixel as well as the subpixels to the right and below it. I then interpolated the texture coordinates for all three. The reason we do so for these added subpixels is to determine the rate of change that happens on our texture relative to our screen and to then use that to determine what mipmap level to sample from. Afterwards, I created the SampleParams struct sp with each point’s interpolated texture coordinates as well as our LevelSampleMethod (lsm) and pixel sample method (psm) as instructed by the project spec. sp is then passed into the helper function sample(), which determines the color for the subpixel which we will discuss later. Finally, we write the returned color to sample_buffer to end the function.

To recall, (x, y) is our pixel location and (u, v) is its corresponding location on the texture represented as a percentage, which holds the color to fill our pixel with. If we move one coordinate on our screen, how much do we move on the texture? We need differentials (dx, dy) to answer this because if the color for the next immediate pixel (on the texture) is far away from the color we just grabbed, we are trying to “squeeze” a big portion of the texture image into a single pixel as mentioned above. We therefore need mipmapping to use a smaller, lower resolution version of the texture to prevent artifacts from forming. The purpose of the helper function get_level() is to find this level.

To implement get_level(), I first calculate the difference vectors, which together is the change in our texture space when moving by 1 pixel (or subpixel) in our screen space. I then scale up these vectors accordingly by the width and height of the full resolution texture image. With these, I finally calculate the mipmap level using the formula seen in lecture and return it.

get_level() is called within our sample() function, which is responsible for determining how to use the mipmap level to find the color of our current pixel/subpixel based on user settings (lsm and psm). If lsm is set to L_ZERO, we sample from resolution 0 as done in task 5. If lsm is set to L_NEAREST, we round our level to the nearest integer and sample from that level (i.e. 1.7 → 2). If lsm is set to L_LINEAR, we sample from both of the neighboring levels (i.e. 1.7 → 1 and 2) and linearly interpolate using the weight as described in the project spec. This is similar to calculating barycentric coordinates with the idea of using a “weight”, except this time we are in 1D instead of 2D. For all three level sampling methods, we sample based on our psm, calling sample_nearest() or sample_bilinear() accordingly. One last detail to mention is that when lsm is set to L_LINEAR and psm is set to P_LINEAR, this combination is known as trilinear sampling.

There are benefits and tradeoffs in using the three techniques implemented: pixel sampling, level sampling, and the number of samples per pixel (supersampling). Here we compare their performance in speed, memory usage, and antialiasing power.

Regarding speed, pixel sampling is the fastest of the three regardless of whether you use nearest neighbor or bilinear sampling because it only samples from a single texture level. Level sampling is slightly slower because it already has pre-computed, lower resolution versions of the texture where it doesn’t need to do much additional computation thanks to these mipmaps. Supersampling is the slowest of the three because it needs to sample multiple times over for every single pixel.

In terms of memory usage, the benefits come in the same order as speed. Pixel sampling uses the least memory because it uses no additional space. Level sampling uses roughly a third more memory in order to store the mipmap layers as we saw in lecture and discussion, so it falls in the middle. Supersampling uses the most memory because as it renders the image at a much higher resolution, it stores the subpixels in a much larger sample_buffer before resolving it to frame_buffer as seen in our implementation in this homework. The size of sample_buffer scales depending on sample_rate which could dramatically increase the amount of memory needed.

When comparing antialiasing power, however, the hierarchy between the three techniques reverses. Supersampling is the best because it actively removes visual artifacts by going through each pixel and blending in the colors of their subpixels, creating a clean transition of colors and a much smoother image. Level sampling comes in second because it addresses a key problem when rendering images in that it fixes texture aliasing in distant objects, though it still doesn’t completely remove jaggies in the rest of the image like supersampling can. Pixel sampling is the worst of the three. Nearest neighbor creates blocky results when higher frequencies are prevalent since it does no blending of colors. Bilinear smoothens the image during magnification as seen in the Italy example from task 5, but fails during minification.

Overall, the three techniques all have their pros and cons depending on the constraints you have and the desired end results. When comparing them all side by side, it makes sense that the higher costs in terms of speed and memory usage result in a higher quality result (supersampling) whereas a cheaper approach gives you images with more unwanted aliasing effects.
