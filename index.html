Task 1: Drawing Single-Color Triangles

Rasterization is the process of taking some 3D geometric object that we want to sample and converting it to the 2D screen we want to display it on. We are essentially “flattening” the object, and we can do so by breaking it down into many triangles to display.

In order to rasterize a single triangle, I modified rasterize_triangle() to iterate through each pixel on the screen and determine whether or not its center (x-coordinate + 0.5, y-coordinate + 0.5) lies inside the triangle. This is done through a binary process: if it does, we fill in that pixel, and if it doesn’t, we don’t, constructing the triangle pixel by pixel. To do this, we use the help of what is called the Point-in-Triangle Test. In this test, each edge of the triangle defines what are called half-planes where the triangle itself is the intersection of three half-planes. For each edge, we determine which side a pixel lies using a mathematical formula that returns a positive number if the pixel is “inside” the edge, a negative number if the pixel is “outside” the edge, and 0 if it lies on the edge. In my implementation, a pixel that lies on an edge is considered inside the triangle, though an improved one would include the OpenGL/Direct 3D Edge Rules to tie-break edges shared by two triangles. If all three edges collectively return a number >= 0 or <= 0 (depending on the winding order of the vertices), then that pixel is inside the triangle.

To make the process more efficient, my algorithm only checks each sample within the bounding box of the triangle, which is the smallest rectangle that can be drawn around the triangle while ensuring the entire triangle is inside it. To find the bounding box, I pulled the minimum and maximum x and y values out of the three vertices given to define the corners of the box. Then, I created a nested loop to iterate through its rows and columns, determining each pixel’s location relative to the triangle and filling them in appropriately. This process uses a helper function isInsideTriangle() that implements the binary process and the Point-in-Triangle Test described above. Since my algorithm checks each sample within the bounding box once, it can therefore be no worse than any algorithm that checks each sample within the bounding box of a given triangle.

I ran into some problems where my images weren’t rendering and I was left with either the outlines of some objects or a completely blank screen, so I knew there was a problem with filling in the pixels. To debug, I began with a smaller problem and worked towards the more complicated one as we learned in lecture. I started by trying to fill in pixels of the entire bounding box to see if my bounding box logic was correct. It wasn’t, and that’s because there was a flaw in my logic of capturing the coordinates of its corners using if statements, INFINITY and -INFINITY, etc. I switched to using the built in std::min() and std::max() functions to make my code cleaner, and the bounding box was then filled in. I then uncommented my code for the Point-in-Triangle test and saw the images properly rendered.


Task 2: Antialiasing by Supersampling

Aliasing is a visual defect that occurs when diagonal or curved lines appear jagged and staircase-like because of the pixel grid of the display. Anti-aliasing techniques are those used to help alleviate this effect. In this task, I implemented supersampling, which is an anti-aliasing technique that renders an image at a much higher resolution before downsampling it to the display.

To begin the supersampling process, I began by modifying both set_sample_rate() and set_framebuffer_target() in order to expand our sample buffer based on sample_rate for each pixel that gets added. Our sample buffer can be thought of as a high resolution grid that is implemented as a 1-dimensional, dynamically resizable Color array and is where we will temporarily store the colors of each subpixel which will be useful later on. Its expansion could be done when the user either resizes the window or changes the sample rate.

Next, I modified rasterize_triangle() from task 1 to iterate through each subpixel within a given pixel. Using various details about the whole pixel, I found the coordinates of the centers of each subpixel to pass into our isInsideTriangle() helper function. I either set that subpixel’s location in sample_buffer to color or did nothing depending on whether it isInsideTriangle(), where its location in sample_buffer is calculated using the pixel’s original index, the screen width, and sample_rate. This process fills up sample_buffer with each subpixel’s color.

Finally, I modified resolve_to_framebuffer() to complete the supersampling process. I iterate through each pixel’s subpixel group in sample_buffer, adding up the red, green, and blue components of their colors. They are then each divided by sample_rate to get the final shades of red, green, and blue to determine the final blended color for the entire pixel. This final color is then assigned in the pixel’s location in rgb_framebuffer_target, a 1D array that represents the final image displayed on our screen.

Collectively, the supersampling process is very useful because by assigning pixel colors to the average color of their subpixels, we smoothen out the transitions in pixel color in jagged edges by blending them together. To antialias our triangles using supersampling, we rendered the image at a higher resolution and stored it in sample_buffer before transferring it to our frame buffer with the appropriate shades of color for each pixel.

Displayed above are results of sampling an image using different sampling rates. Zooming in on the right vertex of the red triangle, we can see the difference supersampling makes. Sampling just once per pixel gives us jagged edges as well as inconsistent colorings where pixels are separated from each other. However, supersampling at 4 and 16 subpixels/pixel gives us very well blended corners where these inconsistent colorings are reduced since the transitions use different shades of red across more pixels.

On a final note, in addition to the modifications to the rasterization pipeline explained above, I also modified fill_pixel() to account for rendering issues regarding points and lines after the supersampling modifications, since points and lines aren’t anti-aliased. To do this, I filled each subpixel within a given pixel all to be the same color the pixel should be.


Task 3: Transforms

In this task, I implemented three transformations that we can apply to objects to change their positions: translation, scaling, and rotation. Depending on the type of transformation, you will have different dimensions and operations to deal with, such as 2D vs. 3D and addition vs. multiplication. We use something called homogenous coordinates to unify all geometric transformations into a single system of matrix multiplications by adding an extra dimension to standard coordinates. In other words, they sync up the entire process into a single “language” to make it faster and easier to perform these transformations. As an example, scaling and rotation are done through multiplication, but translation is done through addition. We can shortcut the process of switching between individual operations on each pixel by using homogenous coordinates to create a single matrix that encapsulates all transformations to be used on all pixels (i.e., shifting, rotating, and translating all at once).

I implemented the three transformation matrices for translation, scaling, and rotation, with rotation being done after converting from degrees to radians to be used with the built in std::sin() and std::cos() functions. Task 4: Barycentric Coordinates

Barycentric coordinates are a coordinate system used to smoothen out attributes of an object, such as a triangle. One common example is interpolating the colors of the three vertices of a triangle to create a blended result. Given a point within a triangle, we can determine its color based on these coordinates that tell you how close it is to each vertex. The barycentric coordinates for a point P are the scalars, or “weights”, (alpha, beta, gamma) that tell you how close P is to each vertex. The closer it is to a vertex, the higher the weight. The further away, the lower the weight. All weights add up to 1 where each weight must be non-negative for the point to lie within the triangle (including on edges).

We can think of each vertex as having a “gravitational pull” on a point. For example, in the image below we have four points located inside the triangle with alpha corresponding to red, beta corresponding to green, and gamma corresponding to blue:

The point on the red vertex is completely red since it lies directly on the vertex, so its barycentric coordinates are (1.0, 0.0, 0.0).

For the point that lies halfway along the red-green edge, its weights are equally split between red and green (and none for blue), so we get a blended red-green color where its barycentric coordinates are (0.5, 0.5, 0.0).

For the point directly in the center of the triangle, all three vertices are equally influencing its color, so its barycentric coordinates are (0.33, 0.33, 0.33).

For the point closest to the blue vertex, its color is predominantly blue with very little red and green influence, though they are still present, so we get a blended red-green-blue color that is more blue defined by the barycentric coordinates (0.10, 0.20, 0.70).
